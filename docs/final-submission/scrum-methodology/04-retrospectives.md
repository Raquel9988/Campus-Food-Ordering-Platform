\# Sprint Retrospective Reports



This document summarises the sprint retrospective reports for the Campus Food Ordering Platform.



Each retrospective records:



\- What went well

\- What did not go well / what could be improved

\- Challenges or blockers

\- Action items for the next sprint



\---



\# Sprint 1 Retrospective Report



\## Sprint 1 Summary



Sprint 1 focused on building the foundation of the platform. The main areas were user verification and menu management.



The team worked on:



\- Student authentication

\- Vendor authentication

\- Admin authentication

\- Role-based access

\- Vendor menu creation

\- Menu display and availability

\- Admin vendor controls

\- GitHub Issues and project board setup

\- Basic CI/CD setup



\## What Went Well



\- The team was able to identify the main Sprint 1 focus areas: user verification and menu management.

\- The basic project direction was established early in the sprint.

\- The team created initial user stories for the main user roles: student, vendor, and admin.

\- Core features such as login, registration, and menu-related functionality began taking shape.

\- The group started using GitHub Issues, branches, and project tracking as part of the Scrum process.

\- By the end of the sprint, the team had enough working functionality to present progress.



\## What Did Not Go Well / What Could Be Improved



\- Sprint 1 was the least organised sprint for the team.

\- Tasks were not separated clearly or fairly at the beginning of the sprint.

\- Some members ended up doing more work than others.

\- Some members were not always sure what they were responsible for.

\- The uneven task split made it harder to track individual contributions.

\- Communication was poor during this sprint.

\- Team members did not always update each other regularly.

\- Some members did not ask questions when they were unsure or stuck.

\- It was difficult to know who was finished, who still needed help, and what still needed to be completed.

\- The team was not properly organised for the sprint review.

\- Presentation roles and explanations were not prepared early enough.

\- Some members needed more time to understand how their own work connected to the full system.

\- The team needed stronger planning, clearer task ownership, better communication, and better preparation before sprint reviews.



\## Challenges / Blockers



\- Tasks were separated poorly at the start of the sprint.

\- Some members carried more work than others.

\- Communication between team members was not consistent.

\- Some responsibilities were unclear.

\- The team was not fully organised for the sprint review.

\- Some members needed more support with GitHub workflow and project structure.

\- Documentation and Scrum evidence were not prepared early enough.



\## Action Items for Sprint 2



\- Split tasks more fairly between all team members.

\- Make sure every member has a clear user story and specific tasks.

\- Use GitHub Issues properly to show who is responsible for each task.

\- Keep the GitHub Projects board updated throughout the sprint.

\- Communicate progress more regularly in the group chat.

\- Ask for help earlier when stuck or unsure.

\- Prepare sprint review roles before the review meeting.

\- Make sure each member understands their own code and can explain it.

\- Start documentation and Scrum evidence earlier instead of leaving it until the end.

\- Improve accountability so that everyone contributes meaningfully.

\# Sprint 2 Retrospective Report



\## Sprint 2 Summary



Sprint 2 focused on the main ordering workflow.



The team worked on:



\- Cart functionality

\- Order placement

\- Orders database and backend logic

\- Vendor orders dashboard

\- Order status updates

\- Student order tracking

\- Real-time updates and notifications



\## What Went Well



\- Task distribution improved significantly compared to Sprint 1.

\- Each member had a clearer and more meaningful contribution.

\- Communication was more effective through regular WhatsApp meetings.

\- The Git workflow improved because members used their own branches.

\- Pull requests were reviewed before merging.

\- The CI/CD pipeline worked smoothly.

\- The team completed all main Sprint 2 tasks on time.

\- Dependency-heavy work was handled early, which allowed other members to continue without major delays.

\- The team had a better understanding of how user stories, tasks, and acceptance tests should be written.

\- The project board was used more effectively to track progress.



\## What Did Not Go Well / What Could Be Improved



\- UML diagrams and architecture documentation were left too late.

\- Some non-coding deliverables were not identified early enough.

\- The team needed to treat documentation as part of the sprint work, not as something to complete at the end.

\- Codecov and some testing tools were confusing for some members.

\- Some small fixes were only noticed close to the end of the sprint.

\- The team still needed to improve how quickly members asked for help when unsure.



\## Challenges / Blockers



\- There were no major blockers.

\- The sprint was short, which created pressure.

\- The main challenge was making sure all dependent features were completed in the correct order.

\- Minor fixes remained near the end, such as notifications and timestamp display.

\- The team had to make sure that backend order data, vendor dashboard updates, and student tracking all connected correctly.



\## Action Items for Sprint 3



\- Start UML diagrams and documentation earlier.

\- Continue prioritising dependency-heavy tasks first.

\- Maintain the Git workflow using feature branches and pull requests.

\- Continue using the GitHub Projects board to track progress.

\- Hold regular meetings to keep everyone aligned.

\- Ask for help earlier when stuck.

\- Make sure all user stories have clear Given-When-Then acceptance tests.

\- Make sure all members understand how their feature connects to the rest of the system.

\# Sprint 3 Retrospective Report



\## Sprint 3 Summary



Sprint 3 focused on adding two major features:



\- Online payments

\- Dietary system



The team worked on:



\- PayFast payment API

\- PayFast Sandbox/test mode

\- Payment notify endpoint

\- Linking payments to orders

\- Preventing unpaid orders from being processed

\- Payment user interface

\- One-vendor cart rule

\- Active orders and order history

\- Dietary tag selection

\- Dietary backend storage

\- Student dietary filtering

\- Updated UML diagrams

\- Integration testing



\## What Went Well



\- The sprint goal was achieved successfully.

\- The payment system was completed and integrated.

\- The dietary system was completed and integrated.

\- The payment feature worked well and became one of the strongest parts of the project.

\- The task split was fair and clear.

\- Most members completed and pushed their work on time.

\- The main branch remained stable after final integration.

\- The team updated UML diagrams to match the new payment and dietary features.

\- There were no major technical problems with Supabase, Cloudflare, or PayFast Sandbox.

\- The team understood the dependency order better than in earlier sprints.

\- The team was able to complete both large features within the sprint.



\## What Did Not Go Well / What Could Be Improved



\- GitHub branch management needed improvement.

\- One team member added new code to an outdated branch, which made merging more difficult.

\- Communication during the sprint could have been better.

\- Team members did not always give regular progress updates in the group chat.

\- Some members did not ask for help early enough when they were unsure.

\- The team needed to check more often that everyone was working from the latest version of the project.

\- Because the sprint was longer, some members forgot certain GitHub commands and needed help near the end.



\## Challenges / Blockers



\- There were no major unresolved blockers.

\- The main issue was GitHub-related, especially outdated branches and merge conflicts.

\- The branch issue was fixed by updating and correcting the affected work.

\- Some members needed reminders to pull the latest version of the project before working.

\- Final integration required extra attention to make sure payment, order status, and dietary filtering worked together.



\## Action Items for Sprint 4



\- Make sure all new work starts from the latest main branch.

\- Pull the latest changes before creating or updating a feature branch.

\- Ask for help earlier when unsure about GitHub, coding, or project requirements.

\- Use the group chat more often for progress updates.

\- Review each other’s work before final merging.

\- Continue keeping the main branch stable.

\- Update UML diagrams whenever the system changes.

\- Make sure every member understands how their work connects to the full system.

\- Keep final documentation organised while coding, instead of leaving it until the end.

\# Sprint 4 Retrospective Report



\## Sprint 4 Summary



Sprint 4 focused on analytics and final project preparation.



The team worked on:



\- Analytics backend/data foundation

\- Analytics dashboard layout

\- Sales per vendor over time report

\- Peak ordering hours report

\- Custom analytics view

\- CSV/PDF export functionality

\- Analytics testing

\- Final submission documentation



\## What Went Well



\- The Sprint 4 task breakdown was clear from the beginning.

\- The work was split evenly between the six members.

\- The analytics dependency order was clearly defined.

\- Person 1 started with the analytics data foundation because all report features depended on clean data.

\- Person 2 created the dashboard structure so that other reports had a clear place in the UI.

\- Persons 3, 4, and 5 could work on different analytics reports in parallel.

\- Person 6 handled exporting once the report data formats were clear.

\- The team used previous sprint lessons to improve planning and avoid unclear task ownership.

\- The analytics feature added value to the admin side of the platform.

\- The team had a clearer understanding of final submission expectations.

\- Scrum evidence was gathered and organised more carefully for final submission.



\## What Did Not Go Well / What Could Be Improved



\- Final documentation took a lot of time and could have been started even earlier.

\- The team needed to make sure all submission links and artefacts were organised in one place.

\- Screenshots, meeting notes, and evidence needed to be packaged more neatly for final submission.

\- Some Scrum artefacts, such as burndown charts, had to be recreated from sprint notes and project progress evidence.

\- The team had to spend extra time checking that the repository, hosted application, and documentation were ready for marking.



\## Challenges / Blockers



\- The main challenge was final organisation rather than coding.

\- The team had many documents and artefacts, so they needed to be structured clearly.

\- Final submission required checking that all links were public and accessible.

\- The team also needed to make sure the repository README and documentation folders were easy for markers to navigate.

\- The final submission required careful checking so that no required artefact was missing.



\## Final Action Items Before Submission



\- Confirm that the hosted application link works publicly.

\- Confirm that the GitHub repository is public.

\- Confirm that the screen recording video is public and under 6 minutes.

\- Confirm that all Scrum artefacts are saved in the repository.

\- Confirm that all additional artefacts are included or linked.

\- Check that the README explains how to navigate the project.

\- Test all links before submitting on Moodle.

\- Make sure the final submission form is completed fully.

\- Make sure the final submission is uploaded before the Moodle deadline.
