## 2. Sprint 1 Retrospective

### Sprint Focus

Sprint 1 focused on the foundation of the platform:

- Student, vendor, and admin authentication
- Role-based access
- Vendor menu management
- Menu display and availability
- Admin vendor controls
- GitHub Issues, project board setup, and basic CI/CD setup

### What Went Well

- The team completed the main Sprint 1 functionality needed for the first review.
- The system foundation was started, including authentication, role-based behaviour, and menu features.
- The team had no major technical blockers during implementation.
- The team was able to identify project workflow problems honestly during the retrospective.

### What Could Be Improved

- Sprint 1 was not organised well enough.
- Tasks were not split clearly or fairly at the start.
- Some members carried more of the main implementation work.
- GitHub was difficult to manage, and members were mostly uploading directly to the `main` branch.
- Task ownership, communication, and sprint review preparation needed improvement.

### Challenges / Blockers

- The team did not yet know how to break user stories into smaller technical tasks.
- The GitHub workflow was not followed correctly.
- Documentation and Scrum evidence were not prepared early enough.

### Action Items for Sprint 2

- Break user stories into smaller tasks before implementation starts.
- Assign each task to a specific team member.
- Use GitHub Issues and GitHub Projects more consistently.
- Use feature branches and pull requests instead of pushing directly to `main`.
- Hold more regular check-ins and ask for help earlier.

## 3. Sprint 2 Retrospective

### Sprint Focus

Sprint 2 focused on the main ordering workflow:

- Cart functionality
- Order placement
- Orders database and backend logic
- Vendor order dashboard
- Order status updates
- Student order tracking
- Notifications / real-time updates

### What Went Well

- Task distribution improved compared to Sprint 1.
- Each member had a clearer contribution.
- Communication improved through regular WhatsApp meetings.
- The team followed a better Git workflow using feature branches and pull requests.
- The CI/CD pipeline worked smoothly.
- All main Sprint 2 tasks were completed on time.

### What Could Be Improved

- UML diagrams and architecture documentation were started too late.
- Some non-coding requirements were not identified early enough.
- Codecov and testing tools were still confusing for some members.
- Some small fixes were only noticed near the end of the sprint.

### Challenges / Blockers

- There were no major blockers.
- The sprint was short, which created time pressure.
- The main challenge was completing dependent features in the correct order.

### Action Items for Sprint 3

- Start UML diagrams and documentation earlier.
- Continue completing dependency-heavy tasks first.
- Keep using feature branches and pull requests.
- Continue using the GitHub Projects board.
- Make sure all members understand how their features connect to the full system.

## 4. Sprint 3 Retrospective

### Sprint Focus

Sprint 3 focused on two major features:

- Online payments using PayFast Sandbox
- Dietary tags and dietary filtering

### What Went Well

- The sprint goal was achieved successfully.
- The payment system was completed and integrated.
- The dietary system was completed and integrated.
- The task split was fair and clear.
- Most members completed and pushed their work on time.
- The main branch remained stable after final integration.
- UML diagrams were updated to include the payment and dietary features.

### What Could Be Improved

- GitHub branch management still needed improvement.
- One team member worked from an outdated branch, which made merging more difficult.
- Progress updates in the group chat were not always consistent.
- Some members waited too long before asking for help.

### Challenges / Blockers

- There were no major unresolved blockers.
- The main issue was GitHub-related, especially outdated branches and merge conflicts.
- Final integration needed extra care to ensure payment, order status, and dietary filtering worked together.

### Action Items for Sprint 4

- Start all new work from the latest version of `main`.
- Pull the latest changes before working on a branch.
- Give more regular progress updates in the group chat.
- Review each other’s work before final merging.
- Keep UML diagrams and documentation updated while coding.

## 6. Overall Retrospective Summary

Across the four sprints, the team improved in:

- Task breakdown
- User story writing
- Acceptance testing
- GitHub Issues usage
- GitHub Projects board tracking
- Branching and pull request workflow
- CI/CD usage
- Integration planning
- Documentation quality
- Communication and team accountability
- Sprint review preparation

The main recurring lessons were:

- Start documentation earlier.
- Keep the project board updated throughout the sprint.
- Communicate progress more regularly.
- Work from the latest version of the code.
- Ask for help earlier when stuck.
- Keep Scrum artefacts organised during the project, not only near submission.
- Split work fairly so that one or two members do not carry most of the sprint.
